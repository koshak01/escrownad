# ЧАСТЬ I. Разбор по пунктам

## A1. Описание и условия сделки не рендерятся — P0

**Симптом.** На странице сделки в полях «Description» и в подзаголовке вместо
текста будут видны теги: `<p>Продаю блок /24</p>`.

**Где.**
```
templates/deals/show.html.tera:11   {{ deal.del_title | default(value="Offer") }}
templates/deals/show.html.tera:12   {{ deal.del_note | default(value="") }}
templates/deals/show.html.tera:38   <dt>Description</dt><dd>{{ deal.del_title | ... }}</dd>
```

**Почему сломалось.** Коммитом `3ad428c` поля `del_title` / `del_note` стали
приходить из редактора Quill, то есть содержат HTML. Tera в `.html`-шаблонах
экранирует вывод по умолчанию — теги превращаются в видимый текст.

**Почему нельзя просто дописать `| safe`.** Санитайзера HTML в проекте
**нет вообще**. Поиск по `ammonia|sanitiz` даёт единственное совпадение —
`wallet_auth.rs:273 sanitize_redirect`, это про URL редиректа, не про HTML.
`deals_save` кладёт `del_title` в базу как есть (`ws_handlers/deals.rs:122-127`).
Сейчас нас спасает ровно экранирование Tera. Поставим `| safe` без санации —
получим XSS: любой владелец кошелька публикует листинг со `<script>`, и он
исполнится у каждого, кто откроет сделку.

**Как чинить.** Двумя частями, обе обязательны:
1. **Санация на входе** — в `deals_save`, до записи в базу: белый список тегов
   (`p, br, strong, em, u, ul, ol, li, a[href], h3, h4, blockquote, code`),
   всё остальное вырезать. Кандидат — крейт `ammonia`; сначала проверить, нет
   ли уже готового хелпера в forge (правило: не дублировать ядро).
2. **Вывод `| safe`** — в шаблоне, только после того как санация встала.

**Как проверить.** Опубликовать листинг с жирным текстом и списком — на странице
сделки должно быть форматирование, а не теги. Затем опубликовать листинг с
`<script>alert(1)</script>` в описании — в базе после санации скрипта быть не
должно, на странице ничего не выполняется.

**Смежное.** На борде `/deals/` теги срезаются функцией `strip_html_one_line`
(`pages/deals.rs:65`) — там всё корректно, борд трогать не нужно.

## A2. Полоса жизненного цикла врёт — P1

**Симптом.** Сделка в статусе `funded`, а шаги «Listed», «Buy request»,
«Accepted» не закрашены — прогресс выглядит сброшенным.

**Где.** `templates/deals/show.html.tera:16-23`. Каждый `<li>` проверяет
равенство текущему статусу:
```
<li class="{% if deal.del_status == 'listed' %}done{% endif %}">Listed</li>
```
То есть класс `done` получает ровно один шаг — текущий.

**Как чинить.** Ввести порядковый номер статуса и красить всё, что `<=` текущего.
Порядок статусов уже определён в `models/deal.rs:11-25`. Аккуратный вариант —
считать индекс на стороне Rust в `DealShowPage::load` (`pages/deals.rs:188`) и
класть в контекст `stage_index`, а в шаблоне сравнивать числа. Ветвление
терминальных статусов (`refunded` / `dispute` / `cancelled` → класс `fail`) уже
есть в строке 23, его сохранить.

**Как проверить.** Провести сделку до `funded` — закрашены должны быть все шаги
до «USDC funded» включительно.

## A3. Кнопки действий видит не та сторона — P1

**Симптом.** Продавец на своём же листинге видит кнопку «I want to buy».
На стадии `accepted` кнопку «Deposit USDC» видят оба. Нажатие даёт ошибку
вида «forbidden: buyer only».

**Где.** `templates/deals/show.html.tera:56-139` — блоки действий условны только
по `deal.del_status`, роль актора не проверяется.

**Что при этом НЕ сломано.** Сервер закрыт корректно: `authorize_action`
(`ws_handlers/deals.rs:250-302`) проверяет сторону на каждое действие, IDOR нет.
Это чисто интерфейсная проблема: пользователю показывают кнопку, которая
гарантированно откажет.

**Как чинить.** В контексте страницы уже есть `usr_id` (`pages/deals.rs:216`).
Добавить в контекст два флага — `is_seller`, `is_buyer` (и `is_creator`) — и
обернуть каждый блок кнопок соответствующим условием. Правила ролей брать не из
головы, а один в один из `authorize_action`, чтобы шаблон и сервер не разошлись.

**Как проверить.** Двумя кошельками: продавец на своём листинге не видит «I want
to buy»; покупатель на стадии `funded` не видит «Start preparation».

## B5. Прод-борд пустой — P0

**Симптом.** `https://escrownad.com/deals/` показывает «No listings yet».
Проверено `curl` сегодня.

**Почему это важнее, чем кажется.** Всё, что у нас сделано хорошо — доска,
жизненный цикл, оракул — не видно вообще. Любой внешний человек (жюри, Atlas со
своей заявкой, партнёр) открывает ссылку и видит пустой каркас.

**Что есть.** Сиды: `seeds/deals.sql` (схема), `seeds/deals_flow.sql`,
`seeds/deals_listing_side.sql`. Наполнения демо-сделками на проде нет.

**Как чинить.** Подготовить набор демо-листингов, покрывающий все состояния:
- пара `offer` в `listed` с настоящими IPv4-префиксами;
- один `request` (спрос на покупку);
- одна сделка в `funded` — чтобы видно было заблокированные деньги;
- одна в `awaiting_proof` — ждёт оракул;
- одна `released` с заполненным `ripe_match_key` — витрина результата.

**Важная тонкость.** Для сделки `released` префикс и стороны надо взять из
**реальной строки** таблицы трансферов RIPE, тогда демо не врёт: обзервер
действительно найдёт этот факт. Это же даст живую проверку оракула
(см. Часть II, шаг 6).

**Как проверить.** Борд показывает строки, у каждой корректны колонки
`Side / Type / Description / Price / Listed / ✓ / Status`.

## B6. Файлы из формы теряются молча — P1

**Симптом.** Пользователь прикрепляет PDF, жмёт «Publish», получает «Offer
published». Файла нигде нет, ошибки нет.

**Где.** Форма отдаёт поле `attachments`:
```
templates/deals/new.html.tera:156   <file_upload name="attachments" multiple={true} ... />
```
Структура параметров хендлера `DealSaveParams` (`ws_handlers/deals.rs:12-55`)
поля `attachments` **не содержит**. Serde спокойно игнорирует лишнее — данные
уходят в никуда без единого сообщения.

**Как чинить.** Решить сначала контур хранения: (а) как forge отдаёт загруженные
файлы в ws-хендлер, (б) где они лежат физически, (в) чем связаны со сделкой —
отдельной таблицей `deals2files` или JSON-колонкой. Это вопрос к ядру
(Гефест) — если в forge уже есть канон загрузки, берём его, свой велосипед не
пишем.

Отдельно: пока хранения нет, **честнее убрать поле из формы**, чем показывать
контрол, который молча всё выбрасывает. Это ровно нарушение твоего правила про
идиотоустойчивость — пользователь уверен, что приложил документ.

## B7. Тумблер «Public listing» не работает — P1

**Симптом.** Пользователь выключает «Public listing», ожидая приватный черновик.
Листинг всё равно уходит на общий борд.

**Где — прямое противоречие в одном шаблоне.**
```
templates/deals/new.html.tera:108   <toggle name="is_public" checked={true} />   ← «OFF = только вы»
templates/deals/new.html.tera:164   <hidden name="publish" value="true" />       ← всегда публиковать
```
В хендлере `publish` читается и запускает `apply_action("publish")`
(`ws_handlers/deals.rs:80-84`, `213-215`), а `is_public` только записывается в
`checklist_json` (`ws_handlers/deals.rs:185-187`) и больше нигде не участвует.

**Как чинить.** Один из двух путей, выбирать тебе:
- **Связать:** `publish = is_public`. Выключен тумблер → сделка сохраняется в
  `draft`, на борде не появляется, владелец видит её в кабинете и может
  опубликовать позже.
- **Убрать тумблер:** если приватных черновиков в продукте не будет, контрол
  лишний и вводит в заблуждение.

Первое честнее и стоит недорого — статус `draft` уже есть в жизненном цикле,
борд его отфильтровывает (`pages/deals.rs:144`).

## B8. Дедлайн и refund по времени не существуют — P1

**Симптом.** В `PROJECT.md` заявлено: «Timeout (~до 30 дней): refund».
Фактически таймаута нет.

**Где.** Поле `deadline_ts` объявлено в `models/deal.rs:62` и **больше не
встречается нигде** — ни в хендлерах, ни в обзервере, ни в шаблонах. Поиск по
всему `src/` и `templates/` даёт только строку объявления.

**Почему это станет критичным на цепи.** Контракт `EscrowLock` принимает
`deadline` параметром при `fund` (см. `contracts/DEPLOY.md`, раздел «Buyer
flow»). Если приложение не умеет его считать и хранить — на цепь нечего
передавать, и деньги покупателя в замке без срока возврата.

**Как чинить.** Проставлять `deadline_ts` при `fund`: «сейчас + N дней», где N —
константа продукта (или поле формы, если хотим договорной срок). Обзервер при
проходе: сделка `funded`/`awaiting_proof` с истёкшим дедлайном → возврат.
Возврат сейчас мок (`chain::mock_refund_tx`), после C13 — вызов `refund` в
контракте.

## B9. Контактный email негде ввести — P2

Модель имеет `contact_email` (`models/deal.rs:67`), хендлер его принимает
(`ws_handlers/deals.rs:34`), **в форме поля нет**. Значит «мягкая проверка
владения по почте» из `PROJECT.md` не имеет входных данных: `soft_verify`
выставляет флаг без единой проверки (`models/deal.rs:157-163`), а `publish`
вообще ставит `soft_verified = true` сразу (`models/deal.rs:232-238`).

Итого галочка «✓» на борде сейчас означает не «продавец проверен», а «продавец
хоть раз завершил сделку» (`sqls/sellers_verified.sql` + `pages/deals.rs:136`).
Это, кстати, честная метрика — но её смысл стоит явно написать в интерфейсе,
иначе галочка читается как верификация личности.

## B10. Мёртвая ветка в обзервере — P2

`bin/observer.rs:57-65` фильтрует статусы `listed | funded | awaiting_proof`
с комментарием «and listed for demo fixtures». Но данные приходят из
`list_deals_listed()` → `sqls/deals_list_open.sql`, где жёстко:
```sql
WHERE del_is_enable AND del_status IN ('funded', 'awaiting_proof')
```
`listed` не придёт никогда. Не баг (лишнего релиза не будет), но комментарий
врёт: если рассчитывали, что оракул подхватит демо-листинги без оплаты — этого
не происходит. Либо убрать ветку, либо, если для демо нужно именно такое
поведение, менять SQL осознанно.

наблюдателя. На машине **не установлены** `cast`, `anvil`, `solc` — Foundry

**C15. Конверсии денег нет.** В базе сумма — `FixedN<8>` (`models/deal.rs:56`),

`checked_*`, с падением при переполнении, а не молча.

## D. Что работает и трогать не надо

- **Оракул RIPE — настоящий.** `src/observer/mod.rs`: тянет живые таблицы
  трансферов RIPE (PA и PI), матчит префикс с проверкой сторон, собирает ключ
  факта. Это самая ценная часть продукта, и она не мок.
- **Обзервер на проде запущен** — `deploy/supervisor/escrownad.conf`, программа
  `escrownad_observer`, приоритет 350, `OBSERVER_INTERVAL_SEC=300`. Крутится
  каждые 5 минут, но открытых сделок нет — работает вхолостую (следствие B5).
- **Вход по кошельку** — MetaMask / Phantom, подпись `personal_sign` в hex
  (`fdd3019` — фикс под Phantom), роль `user`, привязка кошелька к пользователю.
- **Разграничение сторон на сервере** — `authorize_action`, IDOR закрыт.
- **Доска offer / request**, возраст листинга, галочка завершённой сделки.
- **Форма-визард** с подсказками под каждым контролом.
- **Инфраструктура forge** — 4 бинарника + обзервер, IPC по unix-сокетам,
  nginx + supervisor, деплой через Гипериона.

# ЧАСТЬ II. План проверки сервиса

Это следующий шаг по твоему плану — до контракта. Порядок такой, чтобы каждый
следующий шаг опирался на проверенный предыдущий.

> Запуск `cargo` — по твоей команде. Машинный слот компиляции один
> (`cargo --koshak01-status` перед долгой сборкой).

**Шаг 1. Сборка.** `cargo check` целиком — убедиться, что дерево на `f1683da`
собирается без предупреждений.

**Шаг 2. Локальный подъём.** `mprocs` поднимает 4 бинарника (`mprocs.yaml`);
обзервер локально запускается отдельно с `OBSERVER_ONCE=1`. Порты: web `4100`,
ws `4101`. База — `escrownad.com` через туннель `127.0.0.1:5432`
(`etc/database.toml`).

**Шаг 3. Страницы.** Пройти `/`, `/about/`, `/oracle/`, `/deals/`, `/deals/new/`,
`/cabinet/` — каждая отдаёт `200` и не пустая.

**Шаг 4. Вход кошельком.** Подключение MetaMask и Phantom, подпись, появление
пользователя, привязка адреса, выход.

**Шаг 5. Полный жизненный цикл двумя кошельками.**
`publish` → `request` → `accept` → `fund` → `start_prepare` → `mark_prepared` →
`confirm_intent`. На каждом шаге смотреть: правильная ли сторона видит кнопку
(это и есть проверка A3), корректна ли полоса прогресса (A2), читается ли
описание (A1).

**Шаг 6. Оракул на настоящем факте.** Взять реальную строку из таблицы
трансферов RIPE, завести сделку с этим префиксом и сторонами, довести до
`awaiting_proof`, запустить обзервер с `OBSERVER_ONCE=1`. Ожидаем: статус
`released`, заполненный `ripe_match_key`. Это единственная проверка, которая
доказывает, что ядро продукта живое.

**Шаг 7. Отрицательный случай.** Сделка с префиксом, которого в таблицах нет:
обзервер обязан её **не** трогать. Проверяем, что не релизим по случайному
совпадению подстроки — `match_deal` (`observer/mod.rs:81`) сверяет вхождение
префикса в блоки; стоит убедиться, что, например, `10.1.1.0` не матчится на
`110.1.1.0`. **Это отдельный риск, требующий проверки: сравнение идёт через
`contains`, а не по границам блока.**

**Шаг 8. Прод.** Через Гипериона: логи `escrownad_*.log`, состояние группы
supervisor, отсутствие рестарт-циклов; после B5 — борд с демо-данными.

## Что можно сделать красиво — под наш продукт

1. **Нативный USDC + CCTP v2.** На Monad USDC от Circle настоящий, не обёртка,
   плюс CCTP v2, Circle Wallets и Circle Contracts с первого дня. Для эскроу это
   прямое попадание: покупатель приносит USDC **с любой цепи** (Base, Arbitrum,
   Ethereum) быстрым переводом прямо в наш замок. Расчёт в настоящем долларе —
   сильнейший аргумент для RWA-темы.
2. **Circle Paymaster — газ платится в USDC.** Покупателю не нужен MON вообще.
   Снимается главный барьер для не-криптового продавца IP-сетей.
3. **EIP-7702 поддержан.** Даёт объединение `approve` + `fund` **в одну подпись**
   вместо двух транзакций и оплату газа за пользователя. Наша кнопка «Deposit»
   становится честно одной кнопкой.
4. **Прекомпайл secp256r1 (P256) на `0x0100`.** Вход и подпись по **passkey /
   Face ID**, без расширения кошелька. При позиционировании «закрытое финтех-
   приложение, а не крипто-сайт» это самый заметный трюк из доступных.
5. **Скорость под наш WebSocket.** У нас уже есть ws-шлюз. Блок 0.5 с и
   финальность около секунды дают ленту сделки в реальном времени:
   `locked → prepared → RIPE match → released` без спиннеров и перезагрузок.
   На видео это видно за десять секунд.
6. **Контракт до 128 КБ** (против 24 КБ у Ethereum), init-код до 256 КБ.
   Эскроу, диспут и журнал фактов помещаются в один контракт без прокси-нарезки.
7. **Chainlink на Monad** — Data Feeds, Data Streams, CCIP. Даёт второй
   независимый источник факта поверх нашего наблюдателя: «два из двух» вместо
   «поверь нашему ключу». Наличие Chainlink Functions на Monad надо проверить
   отдельно — на нём запрос к RIPE лёг бы идеально.

## Грабли, которые закладываем в архитектуру сразу

- **Газ списывается по `gas_limit`, а не по факту потребления.** Формула
  списания: `value + gas_bid * gas_limit`. Завышенный лимит — реальная
  переплата. Лимиты считаем, «с запасом» не ставим.
- **Асинхронное исполнение, D = 3.** Консенсус отделён от исполнения.
  `eth_getTransactionReceipt` возвращается уже на предложенном блоке, а
  исполнение гарантировано, когда блок ушёл на 3 вглубь. `eth_call` читает
  спекулятивное состояние. **Для нас это означает: успех релиза определяем по
  `receipt.status` после подтверждения глубины, а не по факту «транзакция
  попала в блок».** Ровно твоё правило: результат — по структурному признаку.
- **Свежеполученные токены нельзя тратить ~3.6 с.** Если покупателю только что
  пришли USDC, немедленный `approve/fund` упадёт. Либо ждём, либо объединяем
  пополнение и действие в одну транзакцию контрактом.
- **Reserve balance:** транзакции, которым не хватило средств, всё равно
  попадают в блок и падают при исполнении. Различать «включена» и «выполнена»
  обязательно.
- **EIP-7702:** делегированный внешний адрес не может опускаться ниже 10 MON;
  делегированный контракт не может использовать `CREATE` / `CREATE2`.
- **Blob-транзакции (EIP-4844, тип 3) не поддерживаются.**
- **Полные ноды ограничивают доступ к произвольному историческому состоянию** —
  если понадобится глубокая история, нужен архивный провайдер.

# ЧАСТЬ IV. Порядок работ по контракту

Твоя последовательность: сервис → контракт на тестнете → мейннет.

## Этап 1 — тестнет

1. **Инструменты.** Поставить Foundry (`forge`, `cast`, `anvil`). Осторожно с
   именем: команда `forge` из Foundry не имеет отношения к нашей кузнице.
2. **Ключи и сеть.** Кошелёк наблюдателя, MON из крана, chain id `10143`,
   RPC `https://testnet-rpc.monad.xyz`. Ключ — в окружении процесса, не в
   репозитории.
3. **Ревизия контракта.** `EscrowLock.sol` перечитать до деплоя: кто может
   звать `release`, что происходит при истечении дедлайна, есть ли повторный
   вход, что с переполнением сумм.
4. **Деплой.** Только `EscrowLock` — токен уже существует. Конструктор:
   `(0x534b2f3A21130d7a60830c2Df862319e593943A3, <адрес наблюдателя>)`.
   `MockUSDC` не деплоим (оставляем в репозитории для локального anvil).
   Полученный адрес замка записать в `contracts/DEPLOY.md` и в конфиг.
5. **Режим цепи в коде.** `ChainMode` получает второй вариант — `Live` — и
   читает окружение по-настоящему. Мок остаётся как режим для локальной работы.
6. **Покупатель.** `approve` + `fund` из кошелька в интерфейсе. Проверить, можно
   ли сразу собрать это в одну подпись через EIP-7702 (пункт 3 в Части III).
7. **Наблюдатель.** Совпадение с RIPE → вызов `release` в контракте вместо
   `mock_release_tx`. Проверка результата — по статусу из квитанции с учётом
   глубины D, не по факту отправки.
8. **Дедлайн и возврат** — реальный `refund` по истечении срока (пункт B8).
9. **Сквозной прогон на тестнете:** депозит → подготовка → факт RIPE → выплата
   продавцу. Ссылки на транзакции в эксплорере.

## Этап 2 — мейннет

Переключение сети на chain id `143`, нативный USDC вместо `MockUSDC`, ключ
наблюдателя вынести в защищённое хранение, лимиты газа посчитать (списание идёт
по лимиту), контракт проверить внешним взглядом до первых настоящих денег.
